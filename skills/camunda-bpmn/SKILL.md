# Camunda BPMN Modeling

Create and edit BPMN 2.0 business-flow drafts and executable processes for Camunda 8.8+. You author the **semantic** XML — elements, flows, and known Zeebe extensions. Diagram layout (BPMN DI) is never written by hand; it is generated by `bpmn-auto-layout`.

## Layout is not your job

**Never create, retain, edit, or repair `<bpmndi:BPMNDiagram>` content. Never emit coordinates, dimensions, or waypoints.** Diagram Interchange is produced by the [`bpmn-auto-layout`](https://github.com/bpmn-io/bpmn-auto-layout) tool, not by you. This holds in every context — Copilot hosts and standalone authoring alike.

Your working copy is the semantic BPMN: `<bpmn:definitions>` with processes, flow elements, and sequence flows, no `<bpmndi:BPMNDiagram>` block. Make semantic edits only and preserve unchanged element IDs — layout references elements by ID, so renaming an ID loses its placement.

To produce the renderable file, run the layout tool on your semantic XML:

```bash
npx bpmn-auto-layout@next process.bpmn            # in place
npx bpmn-auto-layout@next process.bpmn --output process.layouted.bpmn
```

Use the latest alpha release, published under the `next` npm tag; the stable release does not include the CLI.

A semantic edit is not a finished user-visible artifact until it has been laid out. You always run the layout yourself — no host or downstream step does it for you. If the tool is unavailable in your environment, install it (`npm install -g bpmn-auto-layout@next`) or say so explicitly; never hand-write DI instead.

## Instructions

### XML Structure

When writing a BPMN file from scratch, follow the canonical bpmn-js style — single-line `<bpmn:definitions>`, two-space indent, no blank lines between siblings, `<el />` self-closing form. Otherwise any round-trip through Camunda Modeler, Web Modeler, or `c8ctl element-template apply` reformats the file, breaking `Edit` matches and adding diff noise. Rules and a worked skeleton: [references/canonical-style.md](references/canonical-style.md).

The `zeebe` namespace, `isExecutable="true"`, and `modeler:executionPlatform="Camunda Cloud"` are mandatory — without them, Camunda won't recognize the process correctly.

Do not hand-write the `<bpmndi:BPMNDiagram>` block. It is generated by `bpmn-auto-layout` after your semantic edits (see “Layout is not your job”). Zeebe deploys a DI-less BPMN happily — the missing DI surfaces only at lint and in Modeler, so the layout step is what makes the file renderable, not something to fix by hand.

### Symbol Encoding

Always encode special characters in XML attribute values:
- `<` → `&lt;`, `>` → `&gt;`, `&` → `&amp;`, `"` → `&quot;`, `'` → `&apos;`

### Core Modeling Rules

Before adding a BPMN element, make sure its purpose and location in the flow are clear from the request or diagram. If a request such as "add a user task" leaves either open to materially different interpretations, ask what the person should do and/or where the task belongs, then wait before editing. Do not turn an adjacent variable or the previous topic into an invented task description. Proceed without asking for optional details that can safely remain unspecified in a draft.

For a request to model a process, produce a business-flow draft unless implementation is requested or already established in the project. Preserve existing configuration, but do not invent worker types, variable contracts, form IDs, decision IDs, or assignment groups to make a draft look executable. Leave unspecified implementation absent and disclose the remaining work, including lint findings; `isExecutable="true"` is not proof of deployment readiness. Do not claim workers are absent or available without runtime evidence.

**Start/End Events:**
- Every path starts with a Start Event (no incoming flows) and reaches an End Event (no outgoing flows)
- Use None start event for most processes; Message for external triggers; Timer for scheduled execution

**Tasks** — one atomic action per task:
- **User Task**: Human interaction. Use the Camunda user task implementation: include `<zeebe:userTask />`. Add `<zeebe:formDefinition formId="X" />` and `<zeebe:assignmentDefinition candidateGroups="..." />` only when the form and assignment are known or requested. Reuse an existing form if it fits. Do not invent and create `X.form` just to satisfy lint when the user asked only for a diagram edit; omit an unspecified form reference, or treat an existing unresolved `formId` as an unfinished draft and call it out explicitly. If the user requests the form or a complete deployment-ready process, author the matching `.form` via **camunda-forms** in the same change. `c8ctl bpmn lint` checks the attribute, not whether the file resolves. Do NOT write the deprecated job-worker variant (no `<zeebe:userTask />`, `formKey` instead of `formId`) — see [references/zeebe-extensions.md](references/zeebe-extensions.md) § Form Definition.
- **Service Task**: Automated work. Executable configuration requires `<zeebe:taskDefinition type="..." retries="3" />`; the type must exactly match worker registration (case-sensitive). Preserve or reuse a known type. If implementation is unspecified in a business-flow draft, leave the task definition absent and disclose the gap rather than inventing a worker contract. When backed by an out-of-the-box connector, apply the template via **camunda-connectors** — don't hand-write the connector input mappings.
- **Script Task**: Inline FEEL expression. Uses `<zeebe:script expression="=..." resultVariable="..." />`.
- **Business Rule Task**: DMN evaluation. Executable configuration uses `<zeebe:calledDecision decisionId="X" resultVariable="..." />`. Reuse an existing matching decision; create `X.dmn` via **camunda-dmn** only when the user requests it or needs a deployment-ready process. Otherwise leave unspecified decision and result-variable contracts absent and disclose the gap; preserve existing references.
- Name tasks with **verb + object** pattern: "Review invoice", "Send notification"

**Gateways:**
- **Exclusive (XOR)**: Exactly one path taken. Label the alternatives. A default flow is a business decision, not a way to avoid incidents: use one only when the fallback is established by the request or existing process. Never route unknown screening or risk results to a successful or lower-risk outcome; do not invent rejection or manual-review policies either. Preserve known conditions and defaults. Leave unspecified variable contracts and routing as a disclosed draft, or ask if the missing decision materially changes the flow. For executable routing, evaluate only agreed conditions; if they are not exhaustive and no fallback is agreed, explain the blocker rather than adding a default. The default is used only when other conditions evaluate to `false`; it does not recover from a FEEL evaluation error. A default flow has no condition. Guard or normalize input only according to the agreed invalid-input policy.
- **Parallel (AND)**: All paths taken concurrently. Always use a matching join gateway to synchronize.
- **Inclusive (OR)**: One or more paths. Also requires a matching join.
- Fix fake-join warnings introduced by your change — join gateways must match their fork type.

**Sequence Flows:**
- Conditions use FEEL expressions with `=` prefix:
  ```xml
  <bpmn:conditionExpression xsi:type="bpmn:tFormalExpression">=amount &gt; 1000</bpmn:conditionExpression>
  ```

**FEEL Expressions in BPMN** — all FEEL must be prefixed with `=`:
- Gateway conditions: `=riskLevel = "HIGH"`
- Timer durations: `="PT7D"` (plain `PT7D` is rejected)
- Input/output mappings: `=customer.name`

Anything beyond a simple variable reference (function calls, operators, context literals, `for` / `every` / `some`) — validate via **camunda-feel** before committing.

**IDs**: Use descriptive PascalCase — `ReviewInvoice`, `AmountExceedsLimit`, `Flow_ToApproval`

### Input/Output Mappings

Create local variables and control variable propagation:

```xml
<zeebe:ioMapping>
  <!-- Input: create local variable from parent scope -->
  <zeebe:input source="=customer.name" target="customerName" />
  <!-- Output: propagate local result to parent scope -->
  <zeebe:output source="=result.status" target="paymentStatus" />
</zeebe:ioMapping>
```

See [references/zeebe-extensions.md](references/zeebe-extensions.md) for detailed variable scoping, propagation rules, and examples.

### Working with Existing BPMN Files

BPMN files can be large. Follow these rules:
1. **Use Grep to find elements** — never read entire files unnecessarily
2. **Use Edit for modifications** — locate the exact section with Grep first, then make precise edits
3. **Read specific sections only** — use offset/limit when needed
4. **Never strip or rewrite DI** — an existing `bpmndi:BPMNDiagram` section carries no semantic information. Ignore it when reading, make semantic edits in place, and let `bpmn-auto-layout` regenerate DI on the next layout run. Re-running layout always replaces DI wholesale, so stale DI is never a problem.

### Hygiene

- Follow canonical bpmn-js style — see [references/canonical-style.md](references/canonical-style.md)
- Self-close empty elements with `<el />` (single space before `/>`)
- Keep unique, descriptive IDs
- Do not add BPMN DI by hand — run `bpmn-auto-layout` to generate it (see “Layout is not your job”)
- Include `<bpmn:incoming>` and `<bpmn:outgoing>` flow references on elements
- **Child elements follow the XSD sequence** — deployment rejects any other order (`cvc-complex-type.2.4.a … One of '{…eventDefinition…}' is expected`): `documentation`, `extensionElements`, `incoming`, `outgoing`, then (events) the `*EventDefinition`. On events, flow refs come **before** the event definition. `c8ctl bpmn format -i <file>` rewrites children into schema order — run it before deploying hand-written XML

### Lint loop — validate within scope

Always run `c8ctl bpmn lint` on the laid-out file. Layout first, then lint: run `bpmn-auto-layout` on your semantic XML, then lint the result. Linting the laid-out file means `no-bpmndi` never fires on your semantic working copy — DI exists by lint time. A modeling draft can still have disclosed, unresolved findings; do not describe it as deployment-ready.

1. Generate layout, then run the linter against the file you touched. Invoke them as **separate tool calls**, not a single shell command or script: a combined exit status cannot tell the user whether layout or lint failed.

   ```bash
   npx bpmn-auto-layout@next path/to/process.bpmn
   c8ctl bpmn lint path/to/process.bpmn
   ```

   `c8ctl bpmn lint` auto-detects the Camunda execution platform version from the BPMN file and applies sensible Camunda defaults. If a `.bpmnlintrc` is present in the project, it is used instead. Stdin also works: `cat process.bpmn | c8ctl bpmn lint`.

2. Fix issues introduced by the edit within the user's requested scope and re-run layout + lint. Report pre-existing or out-of-scope findings rather than changing unrelated elements to silence them. Common categories:
   - **fake-join** — make join gateways match their fork type (XOR forks → XOR joins, AND forks → AND joins)
   - **label-required** — name every labeled element
   - **no-disconnected** — ensure every element is on a complete start-to-end path
   - **no-implicit-split / conditional-flows** — distinguish explicit routing from an implicit split; executable XOR non-default branches need agreed conditions.
   - **gateway safety** — inspect the business meaning of conditions and defaults, including unknown inputs. An all-conditional gateway can raise an incident on unmatched input; disclose that risk or ask for the policy, never invent a benign fallback to clear lint.
   - **superfluous-gateway** — drop pass-through gateways with one in, one out
   - **no-overlapping-elements / no-bpmndi** — a layout concern, never fixed by hand; re-run `bpmn-auto-layout` and, if it persists, report it rather than editing coordinates

3. For an explicitly deployment-ready request, loop until there are zero errors, zero warnings, and no unresolved form or decision references. If the user has not supplied the details needed to make that possible, explain the blocker instead of inventing a form, flow, or configuration. For a draft, report remaining findings and unresolved references; never call it valid or deployable merely because the BPMN linter passes.

If a warning is genuinely a false positive, flag it; do not alter a project-level `.bpmnlintrc` unless the user requests it.

For the repository's deterministic smoke contract, the fixed fixture command is:

```bash
c8ctl bpmn lint process.bpmn
```

### Batch linting and fix guidance

When the task targets a directory (not a single file), use the directory workflow in [references/bpmn-lint.md](references/bpmn-lint.md): discover BPMN files recursively (with skip directories), lint each file, apply targeted fixes, then re-lint until clean.

### Behavioural validation

Lint catches structure, not runtime behaviour (FEEL errors, missing workers, unreachable end events). After lint is clean, validate by **running the process**: prefer **camunda-process-test** for embedded-engine feedback without a cluster, or fall back to **camunda-process-mgmt** to deploy and run an instance.

### Runtime compatibility gate

Before a BPMN change moves to deployment/testing, run a compatibility pass with `c8ctl bpmn lint` against the exact files you intend to deploy (single file or full directory set). This is a required runtime-compatibility check, but it is not by itself a deployment-success guarantee.

Use this troubleshooting mapping when lint flags compatibility issues:

- **implementation/task-definition** failures: task missing required Zeebe extension (`<zeebe:taskDefinition>`, `<zeebe:calledDecision>`, etc.) for its BPMN type.
- **feel / io-mapping** failures: expressions are not valid FEEL for Camunda 8 (for example legacy `${...}` or non-FEEL mapping syntax). Cross-check with **camunda-feel**.
- **element-type / gateway** failures: model uses unsupported or discouraged constructs for the target runtime profile.
- **timer / event-definition** failures: timer or event configuration is structurally present but invalid for runtime execution.

For a full compatibility workflow (target selection, directory runs, and fix loop), use [references/runtime-compatibility.md](references/runtime-compatibility.md).
